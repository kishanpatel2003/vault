## background

The term "harness engineering" crystallized as a named field in the second half of 2025. Mitchell Hashimoto's "My AI Adoption Journey" (Step 5: Engineer the Harness) and Anthropic's "Effective harnesses for long-running agents" (Nov 26, 2025) were the first primary treatments. OpenAI published "Harness engineering: leveraging Codex in an agent-first world" in early 2026, and Anthropic published two follow-on pieces in March 2026: "Harness design for long-running application development" (Mar 24, 2026) and the featured piece "Quantifying infrastructure noise in agentic coding evals." Anthropic also published "Demystifying evals for AI agents" (Jan 9, 2026) and "Effective context engineering for AI agents" (Sep 29, 2025), both of which formalize the theoretical vocabulary around harness components.

This brief supersedes the March 6, 2026 version. It adds four new Anthropic primary sources published between Sep 2025 and Mar 2026, none of which existed at time of the prior brief. Sources: 13 total (up from 9).

## key findings

### Definition and Taxonomy

- An agent harness is the software infrastructure surrounding an LLM that manages everything except the model itself: context lifecycle, tool execution, memory, feedback loops, and architectural constraints. "An AI harness includes prompt engineering as one of its duties (deciding what to feed the model), but goes much further — it manages tools, memory, and the whole loop of interactions." Source: Parallel.ai, "What is an agent harness?", https://parallel.ai/articles/what-is-an-agent-harness
- Anthropic's "Demystifying evals" post (Jan 2026) formalizes a two-harness distinction: an *evaluation harness* (runs evals end-to-end: provides instructions and tools, runs tasks concurrently, records all steps, grades outputs, aggregates results) versus an *agent harness* (enables a model to act as an agent: processes inputs, orchestrates tool calls, returns results). "When we evaluate 'an agent,' we're evaluating the harness and the model working together." Source: Anthropic, "Demystifying evals for AI agents," Jan 9, 2026, https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- Anthropic's "Effective context engineering" (Sep 2025) positions the field as a natural progression: prompt engineering → context engineering → harness engineering. Prompt engineering addresses single-turn instruction quality; context engineering addresses what tokens reach the model at each inference step; harness engineering addresses the full system lifecycle including memory, tools, sessions, and feedback loops. Source: Anthropic, "Effective context engineering for AI agents," Sep 29, 2025, https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- Analytics Vidhya (Dec 2025) frames the stack as three layers: agent framework (SDK/library), agent runtime (execution environment), agent harness (deployment wrapper that manages the full loop). These are distinct roles that may or may not be served by a single tool. Source: Analytics Vidhya, "Agent Frameworks vs Runtime vs Harnesses," Dec 8, 2025, https://www.analyticsvidhya.com/blog/2025/12/agent-frameworks-vs-runtimes-vs-harnesses/

### How Harness Engineering Differs from Prompt Engineering

- Prompt engineering focuses on the content and structure of a single instruction. Harness engineering is the surrounding system: it determines what context reaches the model, how tools are surfaced, how memory persists across sessions, and how outputs are verified. Source: Parallel.ai, https://parallel.ai/articles/what-is-an-agent-harness
- Anthropic's context engineering post explicitly names the field transition: "After a few years of prompt engineering being the focus of attention in applied AI, a new term has come to prominence: context engineering. Building with language models is becoming less about finding the right words and phrases for your prompts, and more about answering the broader question of 'what configuration of context is most likely to generate our model's desired behavior?'" Source: Anthropic, "Effective context engineering for AI agents," https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- OpenAI's harness engineering piece reframes the engineer's job as designing environments, not writing instructions: "what changes when a software engineering team's primary job is no longer to write code, but to design environments, specify intent, and build feedback loops that allow Codex agents to do reliable work." Source: OpenAI, "Harness engineering: leveraging Codex in an agent-first world," https://openai.com/index/harness-engineering/
- Martin Fowler summarizes: harness engineering trades "generate anything" flexibility for reliability — "constraining the solution space: specific architectural patterns, enforced boundaries, standardized structures." Source: Martin Fowler, "Harness Engineering," https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html

### Anthropic Best Practices — Original Harness (Nov 2025)

- **Two-agent structure for long-running tasks.** Split between an *initializer agent* (first session: sets up `init.sh`, `claude-progress.txt`, initial git commit) and a *coding agent* (all subsequent sessions: incremental progress, clean state at end). The two agents share system prompt and tools; they differ only in initial user prompt. Source: Anthropic, "Effective harnesses for long-running agents," Nov 26, 2025, https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- **Feature list as a structured JSON artifact.** Initializer agent writes 200+ granular feature descriptions, all initially `"passes": false`. Coding agents may only toggle the `passes` field. JSON is preferred over Markdown because models are less likely to overwrite or mutate JSON files. Source: Anthropic, "Effective harnesses for long-running agents," https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- **Session startup sequence.** Each coding agent begins: `pwd` → read `claude-progress.txt` and feature list → `git log --oneline -20` → run `init.sh` → verify basic end-to-end functionality → then begin new feature work. This prevents wasted context figuring out the current state. Source: Anthropic, "Effective harnesses for long-running agents," https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- **Git + progress files as state persistence.** Agents commit to git with descriptive messages after each feature; progress files serve as readable handoffs between sessions; git history enables rollback of bad states. Source: Anthropic, "Effective harnesses for long-running agents," https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- **Browser automation for verification.** Puppeteer MCP provides browser access; Claude is required to test features as a human user would before marking them complete. Known limitation: Claude cannot see browser-native alert modals through Puppeteer. Source: Anthropic, "Effective harnesses for long-running agents," https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- **Four canonical failure modes with harness countermeasures.** (1) Agent declares victory too early → feature list JSON; (2) agent leaves broken/undocumented state → progress file + git; (3) agent marks features done without testing → browser automation; (4) agent wastes context figuring out how to run the app → `init.sh`. Source: Anthropic, "Effective harnesses for long-running agents," https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

### Anthropic Best Practices — Evolved Architecture (Mar 2026)

- **GAN-inspired generator-evaluator architecture.** Anthropic's March 2026 paper ("Harness design for long-running application development") introduces a three-agent system: *planner* (expands a 1–4 sentence prompt into a full product spec, instructs itself to be ambitious and avoid granular technical detail), *generator* (implements features one sprint at a time, self-evaluates, commits to git), *evaluator* (Playwright MCP, clicks through the live running app as a user would, grades each sprint against criteria, fails the sprint if any criterion falls below threshold). The generator then iterates against the evaluator's feedback. Source: Anthropic, "Harness design for long-running application development," Mar 24, 2026, https://www.anthropic.com/engineering/harness-design-long-running-apps
- **Context resets as distinct from compaction.** Compaction summarizes prior messages in-place; it preserves continuity but does not give the agent a clean slate, so "context anxiety" (prematurely wrapping up work as context limit approaches) can persist. Context resets clear the window entirely and pass a structured handoff artifact. Anthropic found Claude Sonnet 4.5 exhibited context anxiety strongly enough that compaction alone was insufficient; context resets were essential. Claude Opus 4.5 largely removed context anxiety without resets, allowing a fully continuous session. Source: Anthropic, "Harness design for long-running application development," https://www.anthropic.com/engineering/harness-design-long-running-apps
- **Evaluator skepticism must be tuned explicitly.** Agents reliably praise their own work when asked to self-evaluate, even when quality is mediocre. Tuning a *standalone* evaluator to be skeptical is far more tractable than making a generator self-critical. Once the evaluator produces concrete negative feedback, the generator has something specific to iterate against. This holds for both subjective tasks (design aesthetics) and verifiable tasks (software functionality). Source: Anthropic, "Harness design for long-running application development," https://www.anthropic.com/engineering/harness-design-long-running-apps
- **Grading criteria must encode concrete principles, not subjective judgments.** For frontend design, Anthropic defined four graded criteria: design quality (coherent whole), originality (custom decisions, not AI defaults), craft (typographic hierarchy, spacing, contrast), and functionality (can users complete tasks?). Criteria were calibrated with few-shot examples to reduce evaluator drift. "Is this design beautiful?" cannot be answered consistently; "does this follow our principles for good design?" can. Source: Anthropic, "Harness design for long-running application development," https://www.anthropic.com/engineering/harness-design-long-running-apps
- **Sprint-based progress management.** Generator works one feature at a time, self-evaluates at end of sprint, then hands off to evaluator. If evaluator scores fall below threshold, the sprint fails and the generator retries with detailed feedback. Generator is permitted to make a strategic decision each cycle: refine the current approach or pivot to a different direction entirely. Source: Anthropic, "Harness design for long-running application development," https://www.anthropic.com/engineering/harness-design-long-running-apps

### Anthropic Best Practices — Context Engineering (Sep 2025)

- **Context as a finite resource with diminishing marginal returns.** "Context rot" (Chroma Research) describes how model recall degrades as context window fills — a property across all models. Harness design must treat context as an attention budget, not a dump. Source: Anthropic, "Effective context engineering for AI agents," Sep 29, 2025, https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- **System prompts at the "right altitude."** Too specific → brittle, maintenance-heavy if-else logic. Too vague → model lacks heuristics. Recommended: structured sections (`<background_information>`, `<instructions>`, `## Tool guidance`, etc.) with XML or Markdown delineation. Start with the *minimal* prompt on the best available model; add instructions only where failure modes are observed. Source: Anthropic, "Effective context engineering for AI agents," https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- **Tool set curation is a context engineering decision.** Bloated tool sets cause ambiguous decision points. "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." Tools should be self-contained, robust to error, and unambiguous in their intended use. Source: Anthropic, "Effective context engineering for AI agents," https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- **File system as context architecture.** Folder and file structure determines what can be loaded into context. Claude's agentic search (grep, tail, bash scripts) is preferred over semantic search for its transparency and accuracy; semantic search is only recommended when speed is required. Source: Anthropic, "Building agents with the Claude Agent SDK," Sep 29, 2025, https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk

### OpenAI Best Practices

- **"No manually-written code" as a forcing function.** A zero-human-code constraint surfaced what scaffolding agents actually require. "When something failed, the fix was almost never 'try harder.'" The team built: structured `docs/` knowledge base (AGENTS.md as ~100-line table of contents only), per-worktree isolated app instances, observability tooling (LogQL + PromQL) readable by Codex, browser automation via Chrome DevTools Protocol, and agent-to-agent code review. Source: OpenAI, "Harness engineering: leveraging Codex in an agent-first world," https://openai.com/index/harness-engineering/
- **AGENTS.md as table of contents, not encyclopedia.** Monolithic instruction files: crowd out task context, become stale, cause local pattern-matching. OpenAI's solution: AGENTS.md (~100 lines) with pointers to indexed, versioned `docs/` directories. Enforced by linters and CI jobs. Source: OpenAI, "Harness engineering," https://openai.com/index/harness-engineering/
- **Repository-local, versioned artifacts as the only legible context.** "From the agent's point of view, anything it can't access in-context while running effectively doesn't exist." Slack discussions, Google Docs, and tribal knowledge are illegible; they must be committed to the repo as markdown/schemas/plans. Source: OpenAI, "Harness engineering," https://openai.com/index/harness-engineering/
- **Architectural constraints enforced deterministically.** Custom linters and CI validate knowledge base structure. A recurring "doc-gardening" agent scans for stale documentation and opens fix-up PRs. Source: OpenAI, "Harness engineering," https://openai.com/index/harness-engineering/
- **Productivity claim: ~1/10th time, 3.5 PRs/engineer/day, ~1M LOC in 5 months.** Single-sourced, self-reported, greenfield only. Source: OpenAI, "Harness engineering," https://openai.com/index/harness-engineering/

### Evaluation Frameworks

- **Anthropic "Demystifying evals" taxonomy (Jan 2026)** formalizes the following terms: *task* (single test with defined inputs and success criteria), *trial* (one attempt at a task; multiple trials recommended for statistical stability), *grader* (scoring logic; a task can have multiple graders), *transcript/trace/trajectory* (full record of tool calls, reasoning, outputs), *outcome* (final environment state, distinct from stated output — "Your flight has been booked" vs. a reservation actually existing in the SQL database), *evaluation harness* (infra that runs evals end-to-end), *evaluation suite* (collection of tasks measuring specific capabilities or behaviors). Source: Anthropic, "Demystifying evals for AI agents," Jan 9, 2026, https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- **Three grader types with explicit tradeoffs.** Code-based graders (string match, binary tests, static analysis, outcome verification) are fast, cheap, objective, but brittle to valid variations. Model-based graders (rubric scoring, natural language assertions, pairwise comparison, multi-judge consensus) are flexible and capture nuance, but non-deterministic and require calibration against human graders. Human graders are the gold standard but expensive and slow; primarily used to calibrate model-based graders. Source: Anthropic, "Demystifying evals for AI agents," https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- **Capability vs. regression evals as distinct lifecycle phases.** Capability evals start at a low pass rate (targeting tasks the agent struggles with — a "hill to climb"). Regression evals should have nearly 100% pass rate and protect against backsliding. After launch and optimization, capability evals "graduate" to the regression suite. Source: Anthropic, "Demystifying evals for AI agents," https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- **Infrastructure noise is a first-class eval variable.** Anthropic's "Quantifying infrastructure noise" (featured, ~Apr 2026) found that resource configuration alone can swing Terminal-Bench 2.0 scores by 6 percentage points (p < 0.01) — larger than the leaderboard gap between top models. Below ~3x resource headroom, infra instability (pod OOM kills) dominates; above 3x, extra resources actively help agents solve problems they couldn't otherwise solve. Anthropic recommends specifying both a guaranteed allocation and a separate hard kill threshold per task, not a single pinned value. Source: Anthropic, "Quantifying infrastructure noise in agentic coding evals," https://www.anthropic.com/engineering/infrastructure-noise
- **OpenAI Evals (open-source):** Registry of benchmarks; evaluators write YAML + JSON; string checks and model-graded evals. Source: GitHub, openai/evals, https://github.com/openai/evals
- **OpenAI Evals API (platform):** Three-step: (1) define eval with data schema and graders, (2) upload JSONL test data, (3) run eval with prompt template against model. Async; results via report URL or webhook. Source: OpenAI platform docs, https://platform.openai.com/docs/guides/evals
- **Feature list JSON as inline eval.** Anthropic's harness treats the feature list file as a live regression surface — features are marked `passes: true/false` only after verified end-to-end testing. Lightweight regression harness embedded directly in the agent loop. Source: Anthropic, "Effective harnesses for long-running agents," https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

### Tooling Patterns

- **Claude Agent SDK** (Anthropic): General-purpose agent harness with compaction, context resets, subagent support, tool use, MCP integration. Renamed from Claude Code SDK in Sep 2025. Forms the foundation of all Anthropic harness experiments. Source: Anthropic, "Building agents with the Claude Agent SDK," Sep 29, 2025, https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk
- **Playwright MCP**: Used in the Mar 2026 harness for evaluator agents to click through live running applications, not just static screenshots. Provides navigation, interaction, and visual inspection. Source: Anthropic, "Harness design for long-running application development," https://www.anthropic.com/engineering/harness-design-long-running-apps
- **Puppeteer MCP**: Used in the Nov 2025 harness for browser automation. Known limitation: cannot see browser-native alert modals. Source: Anthropic, "Effective harnesses for long-running agents," https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- **Codex CLI** (OpenAI): Agent runtime integrating with GitHub workflow (gh CLI, PRs, CI). Source: OpenAI, "Harness engineering," https://openai.com/index/harness-engineering/
- **CLAUDE.md / AGENTS.md**: Instruction entry-point files. Claude Code uses `CLAUDE.md`; OpenAI Codex uses `AGENTS.md`. OpenAI caps AGENTS.md at ~100 lines (table of contents); Anthropic's guidance is less prescriptive. Source: Anthropic Claude Code docs, https://code.claude.com/docs; OpenAI, "Harness engineering," https://openai.com/index/harness-engineering/
- **MCP (Model Context Protocol)**: Open standard for connecting agents to external data (Google Drive, Jira, Slack, databases, custom tooling). Used in Claude Agent SDK. Source: Anthropic, "Building agents with the Claude Agent SDK," https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk
- **Git + structured handoff artifacts**: Common across both companies. Used for state persistence, session handoffs, and rollback. Anthropic's Mar 2026 harness adds explicit "context reset handoff artifacts" to carry state cleanly across full context-window resets (distinct from compaction). Source: Anthropic, "Harness design for long-running application development," https://www.anthropic.com/engineering/harness-design-long-running-apps

### Where the Field Is Heading

- **Multi-agent specialization is an open empirical question.** Anthropic: "it's still unclear whether a single, general-purpose coding agent performs best across contexts, or if better performance can be achieved through a multi-agent architecture." The March 2026 work demonstrates that a three-agent planner/generator/evaluator outperforms a single agent on complex tasks — but no controlled comparison to a well-tuned single agent has been published. Source: Anthropic, "Effective harnesses for long-running agents," https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents; "Harness design for long-running application development," https://www.anthropic.com/engineering/harness-design-long-running-apps
- **Context engineering as the successor discipline.** Anthropic explicitly frames context engineering as "the natural progression of prompt engineering" and treats harness design as the domain where context engineering decisions are operationalized. The field is moving from "what to say to the model" → "what to show the model at each step" → "how to architect the full system so the right context is always available." Source: Anthropic, "Effective context engineering for AI agents," https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- **Infrastructure noise as a new eval discipline.** The finding that resource configuration swings benchmark scores by more than the model leaderboard gap is a new research result with no equivalent in static-eval regimes. A new sub-field of "eval infrastructure engineering" is emerging: specifying dual guaranteed/kill-threshold resource parameters, standardizing hardware conditions for public benchmarks, and separating infra-noise variance from model capability variance. Source: Anthropic, "Quantifying infrastructure noise in agentic coding evals," https://www.anthropic.com/engineering/infrastructure-noise
- **Harnesses as the new service templates.** Fowler speculates teams will select from harness templates for common application topologies, analogous to service templates. Open questions on versioning, forking, and synchronization. Source: Martin Fowler, "Harness Engineering," https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html
- **Human attention remains the binding constraint.** OpenAI: "our one truly scarce resource: human time and attention." Agent-to-agent code review is nearly full in OpenAI's deployment (human review optional). The trajectory is toward minimal-touch harnesses where human intervention surfaces are narrowed to task specification and edge-case review. Source: OpenAI, "Harness engineering," https://openai.com/index/harness-engineering/

## source tensions

**Productivity claims remain single-sourced and self-reported.** OpenAI's "1/10th the time" and "3.5 PRs/engineer/day" have no independent replication. Fowler explicitly flags this conflict of interest. The codebase was greenfield; brownfield applicability is unverified. No update from any source in the past month has provided corroborating data.

**Context resets vs. compaction: model-dependent.** Anthropic's March 2026 paper found Sonnet 4.5 required context resets because compaction alone did not eliminate context anxiety. Opus 4.5 removed this behavior, making continuous sessions viable. This means harness design is not model-agnostic: a harness optimized for Sonnet 4.5 may be unnecessarily complex on Opus 4.5, and vice versa. No guidance exists yet for selecting the appropriate context management strategy based on model characteristics.

**Self-evaluation is structurally unreliable — but evaluator calibration is underspecified.** The March 2026 paper establishes that agents praise their own work regardless of quality, and that a standalone evaluator is easier to tune skeptical. However, "calibrating the evaluator using few-shot examples" is described only qualitatively — no quantitative threshold, no inter-rater reliability data, no guidance on how many calibration examples are needed or how to detect evaluator drift over long runs.

**Infrastructure noise paper is featured but methodologically narrow.** The 6 percentage point finding is from Terminal-Bench 2.0 on a GKE cluster with a specific enforcement methodology. The SWE-bench crossover showed a smaller effect (1.54 pp). Generalizability to other benchmarks, other infrastructure stacks, and non-coding domains is unverified. The paper acknowledges it has not "rigorously tested" the effect on non-Anthropic models.

**Term "harness engineering" is still not standardized.** Anthropic's Demystifying Evals post (Jan 2026) uses "agent harness" and "evaluation harness" as distinct terms. OpenAI uses "harness engineering" as a practice label. Parallel.ai uses "agent harness" as a product category. Fowler uses it as a design discipline. There is no cross-company standard definition as of April 2026, approximately 8 months after the term's emergence.

**Sources were uniformly consistent on one point:** the model is not the primary determinant of agent system quality. This claim appears in Anthropic, OpenAI, Fowler, Parallel.ai, Hashimoto, and the Medium "2026 is agent harnesses" piece — no contrary evidence found in any source reviewed.
